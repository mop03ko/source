# Хуваарийн давтан ачаалалт ба кэш

## Илэрсэн шалтгаан

CRM Google Sheets-ийг анх нээх, цонхонд буцаж ирэх, 30 секунд тутам синк хийдэг. Амжилттай HTTP хариу бүр нийт `refresh`-ийг нэмэгдүүлж, хуваарийн URL дахь `refresh` параметрийг өөрчилж байсан. `useRemote` шинэ URL бүрд өмнөх өгөгдлийг арилгадаг тул хүснэгт түр алга болж, дахин ачаалсан мэт харагдаж байв. Мөн “Манай баг”-ийн доор болон тусдаа цэсэнд ижил хуваарь байрлаж байсан.

## Хэрэгжүүлсэн

- “Баг ба хуваарь” гэсэн нэг үндсэн цэс, дотор нь Ant Design-ийн “Ажлын хуваарь”, “Манай баг” табууд. Өмнөх `?view=schedule` болон `?view=team` холбоосууд ажиллана. Тусгаарлагдсан эрхүүд өөрийн хуваарийн табыг ашиглана; гишүүн засах эрх өөрчлөгдөөгүй.
- Хуваарийн manual refresh-ийг Sheets-ийн refresh-ээс тусгаарлав. Сарын тогтвортой URL ашиглана.
- Хэрэглэгчийн и-мэйл, эрх, нэр, идэвхтэй төлөвөөр тусгаарласан, тухайн CRM цонхны санах ойд хадгалах кэш: 30 секундийн freshness, хамгийн ихдээ 12 сарын хариу.
- Ижил URL-ийн зэрэг эхэлсэн хүсэлтүүд нэг Promise хуваалцана. Кэш хүчинтэй үед таб/сар руу буцахад сервер дахин дуудахгүй.
- Хугацаа дууссан өгөгдлийг харуулж байхдаа шинэчилнэ. Нээлттэй хуудсанд 60 секунд тутам, мөн цонхонд буцаж ирэхэд хугацаа дууссан өгөгдлийг шалгана. Далд цонхноос polling хийхгүй.
- Хадгалах, хүсэлт шийдвэрлэх, цуцлах, manual refresh хийхэд бүх сарын кэшийг хүчингүй болгоно. Бусад сарын хүлээгдэж буй хүсэлтүүд ч өөрчлөгдөж болох тул зөвхөн тухайн сарыг цэвэрлээгүй.
- Хүчингүй болгохоос өмнөх удаан хариу кэшийг буцаан дүүргэхгүй. 401/403 үед өмнөх хүснэгтийг цэвэрлэнэ. Алдаатай хариуг кэшлэхгүй.

## Сайтын бусад хэсэгт кэш ашиглах боломж

| Өгөгдөл | Шийдэл / санал |
|---|---|
| JS, CSS зэрэг хувилбарлагдсан статик файл | Одоо Next/Vercel кэш ажиллаж байна. Production CSS дээр `public,max-age=31536000,immutable`, `x-vercel-cache: HIT` ажигласан. Давхар өөр кэш шаардлагагүй. |
| Хуваарийн сарын GET | Дээрх богино, хэрэглэгчээр тусгаарласан клиент кэш хэрэгжсэн. |
| Агуулахын сонголтын жагсаалт: салбар, брэнд, суваг | Ижил зарчмыг дараагийн өөрчлөлтөөр өргөтгөж болно. Агуулах/бараа/сувгийг нэмэх, засах үйлдэл бүрд invalidation холбох шаардлагатай. Одоогоор хэрэгжүүлээгүй. |
| Барааны үлдэгдэл, үнэ, зээл батлах, төлбөр, эрх | Нийтийн CDN кэш тохирохгүй. Худалдан авалт батлах мөчид серверийн шинэ мэдээлэл, эрхийн шалгалт зайлшгүй. Одоогийн `no-store`-ийг хэвээр үлдээсэн. |
| Нийт CRM-ийн суурь өгөгдөл | Хуваарь нээлттэй байхад ч `/api/crm` статистик татаж байна. Дараагийн оновчлол: хэрэглэгч/цэсний суурь өгөгдлийг борлуулалтын статистикаас тусгаарлах, идэвхгүй панелийн JS-ийг хэрэгтэй үед нь ачаалах. Энэ өөрчлөлтөөр бүх API-г кэшлээгүй. |

`no-store` нь HTTP кэшийн удирдлага; энд хэрэгжүүлсэн богино санах ойн кэш нь зөвхөн аппын уншилтын давталтыг багасгана. localStorage, service worker, нийтийн серверийн кэш ашиглаагүй. Хуудсыг бүтнээр дахин нээхэд кэш шинээр үүснэ. Нийт сайтын хурд хэдэн хувиар өссөн гэсэн хэмжилт хийгээгүй; баталгаажуулалт нь хуваарийн хүсэлтийн тоо, хүснэгт тасралтгүй харагдах ажиллагаанд төвлөрсөн.

## Шалгах командууд

- `npm run lint`, `npm run build`, `npm test`
- `node tests/request-cache.test.cjs`: зэрэг хүсэлт, TTL, invalidation, удаан хариу, хэрэглэгчийн тусгаарлалт, алдаа, багтаамж.
- `node scripts/schedule-ui-audit.mjs`: анхны болон Sheets polling-ийн хүсэлтийн тоо, таб/Back/Forward, manual refresh, хадгалалт, эрхийн алдаа, mobile.
- `node scripts/ux-audit.mjs`: бусад модулийн үндсэн ажиллагаа.

Эдгээр шалгалт бүгд тэнцсэн. Локал production build-ийн браузерын туршилтаар: анхны хуваарийн GET = **1**; таб/Back/Forward болон Sheets-ийн 30 секундийн polling-ийн дараа = **1**; manual refresh-ийн дараа = **2**. Удаашруулсан хариу хүлээхэд хүснэгтийн DOM солигдоогүй. 403 хариу өгүүлэхэд хуучин мөрүүд арилж, Retry хийсний дараа сэргэсэн. Артефакт: `artifacts/schedule-ui/evidence.json`.

Эх сурвалж: [Next.js caching](https://nextjs.org/docs/app/guides/caching-without-cache-components), [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control). Клиент кэшийн хэмжээ, TTL, invalidation хүрээ нь энэ CRM-ийн кодын уншилт болон эрхийн загварт тулгуурласан хэрэгжилтийн сонголт.
