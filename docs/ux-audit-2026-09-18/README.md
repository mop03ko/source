# AntMall CRM — UX/UI шинжилгээ

Огноо: 2026-09-18. Локал production build, Chrome headless, хиймэл өгөгдөл.

## Ерөнхий дүгнэлт

Сайт нь нэгдсэн өнгө, танигдах sidebar, ажилтны эрхээр ялгасан модулиуд, хүсэлт–холбоо барилт–түүх гэсэн ойлгомжтой үндсэн бүтэцтэй. Desktop дээр ажлаа хийх суурь хангалттай. Харин гар утасны дэлгэц, уншигдах байдал, календарийн мэдээлэлд хүрэх боломж, алдаанаас сэргэх урсгалд засах шаардлагатай асуудлууд байна. Эхлээд эдгээрийг засах нь гоёлын redesign хийхээс илүү шууд үр дүнтэй.

Энэ тайланд **22 асуудал** нэгтгэв: **10 нь P1**, **12 нь P2**. P1 нь чухал мэдээлэл харах, ажлаа үргэлжлүүлэх, мэдээллээ хадгалах эсвэл зөв ойлгоход шууд нөлөөлнө. P2 нь ажлын хурд, ойлгомж, суралцах хугацаа, хүртээмжийг доройтуулна. Энэ ангилал нь аудитын эрэмбэлэлт; бүх асуудлыг WCAG зөрчил эсвэл серверийн эвдрэл гэж үзээгүй.

## Хамрах хүрээ ба нотолгоо

- 1440×1000 desktop, 390×844 болон 320×740 CSS px viewport.
- Админ эрхтэй туршилтын session; 18 хүсэлт, маркетингийн 4 ажил, IT-ийн 4 ажил, 3 туршилтын ажилтан.
- Өнөөдрийн ажил, борлуулалт, календарь, хүсэлтийн дэлгэрэнгүй/засвар, хяналтын самбар, маркетинг, IT, профайл, Sheets тохиргоо, SMS-ийн алдаа, чат, нэвтрэх хуудсыг шалгасан.
- 21 screenshot, DOM хэмжээ, сонголт/refresh-ийн үр дүн, браузерын exception-уудыг [evidence.json](evidence.json)-д хадгалсан.
- SMS дүрмийн API-г зөвхөн туршилтын браузерт түр блоклож, холболт тасарсан төлөвийг шалгасан. Бодит SMS илгээгээгүй.
- UI snapshot-ийн өгөгдөл бүгд зохиомол. Бодит DB, OAuth, Sheets, SMS, production домэйнд өөрчлөлт оруулаагүй.
- Mobile нь Chrome-ийн viewport simulation; бодит iPhone/Android, дэлгэцийн гар, Safari, VoiceOver/NVDA, touch gesture, 200–400% zoom-ыг бүрэн туршаагүй.
- Бүх эрхийн browser flow, хэрэглэгчийн ярилцлага, бодит ажлын гүйцэтгэлийн хугацаа болон Core Web Vitals хэмжээг хамруулаагүй. Тиймээс хэрэглэгчийн судалгааны оноо, WCAG certification гэж үзэхгүй.
- Кодын хүрээ нь аудитын үеийн локал хувилбар. Шинжилгээний явцад бүтээгдэхүүний код засварлаагүй.

## Сайн ажилласан хэсгүүд

1. Нил ягаан sidebar, цагаан ажлын хэсэг, улбар шар үндсэн үйлдэл нь брэндийн танигдах өнгөний систем үүсгэсэн.
2. Sidebar-ийн идэвхтэй хэсэг өнгө, зүүн тэмдэглэгээ, текстээр ялгарна.
3. Борлуулалт, маркетинг, IT-ийн ажлыг эрхээр ялгаж, ижил хүснэгт/календарь/тайлангийн хэв маяг ашигласан.
4. Хүсэлт нээхэд жагсаалтын орчноо алдалгүй хажуугийн дэлгэрэнгүй гардаг. Холбоо барилт, мэдээлэл, түүх тусдаа.
5. Хугацаа хэтэрсэн ажил, шинэ хүсэлт, opt-out зэрэг төлөвийг текст болон өнгөөр хослуулсан.
6. Хүсэлт устгах, холбоо барихыг зогсоох үед тайлбар, шалтгаан, баталгаажуулалт шаардана.
7. Улаанбаатарын цагийн бүс, импортын хязгаар, SMS/Messenger-ийн тэмдэглэл ба бодит илгээлтийн ялгааг тайлбарласан.
8. Label, хэд хэдэн aria-label, Radix dialog/tab, focus-visible, reduced-motion, mobile input-ийн 16 px хэмжээг ашигласан сайн суурь байна. Гэхдээ энэ нь бүрэн хүртээмжийг батлахгүй.

## Түрүүлж засах асуудлууд — P1

### 01. Mobile навигац хуудасны өргөнийг эвдэж байна — браузераар батлагдсан

390 px viewport дээр борлуулалтын document scrollWidth **651 px**, тохиргооных **508 px**. Борлуулалтын tablist өөрөө **635.11 px**, тохиргооных **492.44 px** өргөн. 320 px дээр ч борлуулалтын scrollWidth 651 px хэвээр. Хэрэглэгч зөвхөн хүснэгтээ бус бүх хуудсаа хажуу тийш гүйлгэх шаардлагатай болж, баруун талын табууд тасарна.

Нотолгоо: [борлуулалт mobile](11-sales-mobile.png), [тохиргоо mobile](14-settings-mobile.png), [320 px](13-calendar-320.png). Код: `app/globals.css` дахь `.sales-tabs`, `.settings-tabs`; `components/ui/tabs.tsx`.

Шийдэл: табуудыг өөрийн хязгаарлагдсан scroll container-д байрлуулах, сонгосон tab-ыг харагдах хэсэгт шилжүүлэх; mobile дээр dropdown ашиглах хувилбарыг турших. Эцэг flex/grid элементүүдийн min-width, overflow-ийг хамт засах.

Хүлээн авах шалгуур: 320/360/390/768 px дээр document-level horizontal scroll үүсэхгүй; бүх таб touch болон keyboard-аар хүрэх боломжтой. Өгөгдлийн хүснэгтийн тусдаа хэвтээ scroll зөвшөөрөгдөнө. WCAG reflow-д хүснэгтийн тусгай нөхцөл байдаг тул бүх хүснэгтийн scroll-ийг автоматаар зөрчил гэж тооцохгүй. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

### 02. Desktop dashboard-ийн KPI мэдээлэл тасарч байна — зурагт батлагдсан

1440 px дээр борлуулалт болон маркетингийн том карт доторх гурав дахь багана баруун захаараа тасарна. `repeat(3,1fr)` дотор дахин 3 баганатай `.sync-summary` хийсэн бөгөөд картын `overflow:hidden` мэдээллийг нууж байна. “Идэвхтэй Recycle”, “Худалдан авсан”, хугацаа хэтэрсэн болон төсвийн хувь зэрэг мэдээлэл бүтэн харагдахгүй.

Нотолгоо: [dashboard](05-dashboard-desktop.png). Код: `app/dashboard-panel.tsx`, `app/globals.css` дахь `.budget-cards`, `.sync-summary`, `.panel`.

Шийдэл: картын бодит өргөнд тулгуурлан 1–2 багана болгох, `minmax(0,1fr)`, `min-width:0`, текстийн мөр шилжилт тохируулах. Том мөнгөн дүнг заавал бүтнээр нь унших боломжтой болгох.

Хүлээн авах шалгуур: урт Монгол label, 9 оронтой төсөв, 1280/1440 px дээр нэг ч тоо эсвэл тайлбар далдлагдахгүй.

### 03. Календарь 3-аас олон ажлыг нээх замгүй; mobile grid мөн гаждаг — батлагдсан

Туршилтын нэг өдөр 18 хүсэлттэй байхад 3-ыг харуулж, **“+15 илүү”** гэж бичсэн. Энэ элемент `SPAN`, `tabIndex=-1`, click handler байхгүй. Үлдсэн ажлыг тухайн өдрөөс нээх боломжгүй. 390 px зурагт урт хүсэлтийн нэртэй өдрийн багана бусдаасаа хэт өргөсөж, сарын нүднүүд жигд бус болсон.

Нотолгоо: [desktop calendar](03b-calendar-content.png), [mobile calendar](12b-calendar-content-mobile.png), `app/month-calendar.tsx`.

Шийдэл: “+N илүү”-г тухайн өдрийн бүх ажлыг харуулах dialog/жагсаалт нээдэг button болгох. Grid-д `repeat(7,minmax(0,1fr))`, event-д min-width/ellipsis; mobile-ийн үндсэн хувилбарт өдрийн agenda жагсаалт санал болгох.

Хүлээн авах шалгуур: 0/1/3/4/50 ажилтай өдрийг шалгаж, бүгдийг mouse/keyboard-аар нээнэ. Урт нэртэй event долоо хоногийн багануудыг эвдэхгүй.

### 04. Үндсэн үйлдэл болон туслах текстийн contrast хангалтгүй — хэмжсэн

CSS-ийн foreground/background утгаар WCAG relative luminance томьёогоор тооцсон:

| Элемент | Өнгө / суурь | Ялгарал |
|---|---|---:|
| Үндсэн товчны цагаан текст | `#ffffff` / `#f38a30` | **2.47:1** |
| Хүснэгтийн гарчиг | `#9b8ea7` / `#faf9fc` | **2.94:1** |
| Мөрийн туслах текст | `#9a8ca6` / `#ffffff` | **3.15:1** |
| `.muted` текст, цагаан гадаргуу дээр | `#837a8e` / `#ffffff` | **4.09:1** |
| Маягтын тусламж | `#a091aa` / `#ffffff` | **2.95:1** |
| Footer | `#b0a4b9` / `#f7f7fa` | **2.22:1** |

Браузерын computed style үндсэн товчны цагаан/улбар шар өнгийг баталсан. Энгийн текстэд 4.5:1, том текстэд 3:1 босго хэрэглэнэ; disabled control болон logo-д өөр нөхцөл үйлчилнэ. Энд идэвхтэй жижиг текстийг үнэлсэн. [W3C Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

Шийдэл: action өнгийг бараан болгох эсвэл хангалттай бараан текст хэрэглэх; muted/helper/table-header өнгийг нэг token системээр засах. Зөвхөн үсгийг томруулахад энэ асуудал бүхэлдээ шийдэгдэхгүй.

Хүлээн авах шалгуур: default/hover/focus төлөвийн бүх идэвхтэй жижиг текст ≥4.5:1; бодит background тус бүрээр дахин хэмжих.

### 05. SMS API унахад төгсгөлгүй ачаалалтын төлөв үзүүлнэ — зориудын алдаагаар баталсан

`/api/sms-rules`-ийг browser түвшинд блоклоход “Ачаалж байна…” хэвээр, alert болон retry гараагүй. Кодын `catch` error хадгалдаг ч `rules===null` гэсэн эрт return алдааны UI-г харуулахгүй байна.

Нотолгоо: [SMS error](08c-sms-error.png), `evidence.json → checks.smsBlocked`, `app/sms-rules-panel.tsx`.

Шийдэл: loading/error/empty/success төлөвийг тусад нь илэрхийлж, алдаа гарвал spinner-ийг зогсоох; “Дахин оролдох” үйлдэл нэмэх.

Хүлээн авах шалгуур: offline/403/500/timeout үед ойлгомжтой алдаа, retry; амжилттай боловч хоосон хариуг алдаанаас ялгаж харуулна.

### 06. Календарь болон IT/маркетингийн тайлангийн алдаа хэрэглэгчээс нуугдана — кодоор батлагдсан

Calendar/report fetch-ийн `catch` хоосон. Сүлжээ эсвэл API алдаа гарвал хоосон календарь, өмнөх мэдээлэл эсвэл тайлангүй хэсэг харагдаж болно. Хэрэглэгч үүнийг “ажил алга” гэж андуурна. Энэ failure path-ыг бүх модульд браузераар зориуд үүсгээгүй.

Код: `app/crm.tsx`, `app/it-panel.tsx`, `app/marketing-panel.tsx`.

Шийдэл: модуль бүрийн error state, дахин оролдох, “өмнөх мэдээлэл харуулж байна” тэмдэглэгээ, сүүлд амжилттай шинэчлэгдсэн цаг.

Хүлээн авах шалгуур: API унасан үед “ажил алга” гэсэн success-empty төлөв гарахгүй; хуучин мэдээлэл шинэ хугацааны тайлан мэт харагдахгүй.

### 07. Хадгалаагүй ажил алдагдах хамгаалалт дутуу — кодын урсгалаар тогтоосон

Dialog/sheet-ийг хаах, өөр хэсэгт шилжихэд form dirty эсэхийг шалгахгүй. Хүсэлтийн тайлбар, засвар, Sheets mapping, SMS дүрмийн бичиж буй агуулга unmount болох үед алдагдах боломжтой. Sheets-ийн dirty тэмдэглэгээ зарим үйлдлийг хориглодог ч гарахыг хамгаалахгүй.

Код: `app/crm.tsx` дахь dialog/sheet-ийн `onOpenChange`, `app/settings-panel.tsx`, `app/sheets-panel.tsx`.

Шийдэл: өөрчлөгдсөн form-д “Хадгалах / Өөрчлөлтөө хаях / Үргэлжлүүлэн засах”; чатын draft-ыг харилцан яриагаар хадгалах. Нууц credential-ийг browser persistent storage-д автоматаар хадгалахгүй.

Хүлээн авах шалгуур: Escape, X, backdrop, module/tab солих, refresh бүрээр dirty form-ыг шалгах. Хоосон form-д шаардлагагүй confirmation бүү гаргах.

### 08. SMS дүрмийн switch нь хадгалах товчны үүргийг далд гүйцэтгэдэг — кодоор батлагдсан

Дүрмийн текстийг өөрчлөөд “Хадгалах” дараагүй байсан ч switch дарахад `toggle()` нь одоогийн `message`-ийг API руу илгээдэг. Хэрэглэгч зөвхөн асаах/унтраах гэж бодоод draft текстээ нийтэлж болно. Delete нь баталгаажуулалтгүй, буцаах UI-гүй.

Код: `app/sms-rules-panel.tsx → RuleRow.toggle/remove`.

Шийдэл: switch зөвхөн идэвхтэй төлөвийг өөрчлөх; эсвэл бүх өөрчлөлтийг нэг explicit “Хадгалах” үйлдлээр баталгаажуулах. Устгах үед нэртэй баталгаажуулалт эсвэл undo өгөх.

Хүлээн авах шалгуур: draft текст бичээд switch дарахад текст хэрэглэгчийн тодорхой зөвшөөрөлгүй хадгалагдахгүй.

### 09. Календарийн харагдац дээр зарим шүүлтүүр үйлчлэхгүй — кодоор батлагдсан

Борлуулалтын “Ирсэн огноо” хоёр талбар календарь дээр харагдсаар байдаг. Гэтэл календарийн хүсэлтэд `view,calendar,month,q,status,owner` л дамждаг; `dateFrom/dateTo` байхгүй, effect dependency-д ч ороогүй. Огноо сольсноор жагсаалтын count өөрчлөгдөж болох ч календарь тэр хүрээг дагахгүй.

Код: `app/crm.tsx` calendar effect болон `.filters`.

Шийдэл: календарьт бүх харагдаж буй filter-ийг хэрэгжүүлэх, эсвэл хамаарахгүй талбаруудыг нууж, “товын огноо” ба “ирсэн огноо”-г ялгаж тайлбарлах.

Хүлээн авах шалгуур: ижил шүүлттэй list/calendar-ийн багцын утга ойлгомжтой, count болон үйл явдал хоорондоо зөрчилдөхгүй.

### 10. Анхны ачаалалт болон refresh дээр React hydration алдаа гарсан — runtime баталгаа

Browser exception log-д **React #418 хоёр удаа** бүртгэгдсэн. Энэ нь серверийн HTML ба клиент текст таарахгүй, React тухайн модыг клиентэд дахин үүсгэж байгааг илэрхийлнэ. [React-ийн тайлбар](https://react.dev/errors/418)

Нотолгоо: `evidence.json → errors`. Browser зурагт “September 18, 2026”, “September 2026” харагдсан; Node-ийн `Intl.DateTimeFormat('mn-MN')` нь “2026 оны есдүгээр сарын 18” гаргасан. Иймээс locale fallback нь магадлалтай шалтгаан; яг component/stack-ийн эх шалтгааныг dev build-ээр тусад нь тогтоох шаардлагатай. Текстийн зөрүүтэй огнооноос гадна render үеийн цагийн утгуудыг мөн шалгана.

Шийдэл: серверээс тогтвортой огнооны snapshot дамжуулах, сервер/клиентэд ижил Монгол формат ашиглах. Warning-ийг нуухын оронд үүсгэж буй зөрүүг засах.

Хүлээн авах шалгуур: цэвэр profile дээр анхны load болон refresh бүрд hydration exception 0; browser locale солих, өдөр солигдох заагийг турших.

## Ажлын урсгал, ойлгомж, хүртээмж — P2

### 11. URL сонгосон хэсгийг илэрхийлэхгүй

Браузерын туршилтаар “Бүх хүсэлт” дээр URL `/` хэвээр; refresh дарахад “Хяналтын самбар” руу буцсан. Tab/filter/lead нь React state-д хадгалагдана. Ажилтан яг тухайн хүсэлт, тайлангийн шүүлттэй холбоос хуваалцах боломжгүй.

Санал: view, filter, page, lead ID-г route/query-д хадгалах. Back/Forward болон refresh сонголтыг сэргээдэг байх. Нотолгоо: `evidence.json → checks.beforeReload/afterReload`.

### 12. Тайлангийн хугацааны утга нэг мөр ойлгомжтой биш

Dashboard нь бүх хугацааны operational stats болон сонгосон хугацааны distribution/report-ийг нэг дэлгэцэд хослуулдаг. IT/маркетингийн report нь `created_at`-аар шүүсэн ажлын одоогийн `done` статусыг тоолдог ч “Сонгосон хугацаанд хаагдсан” гэж бичсэн. Энэ нь хаагдсан огноогоор хэмжсэн мэт ойлгогдоно.

Санал: “Тухайн хугацаанд үүссэн ажлуудаас одоо дууссан” гэж зөв нэрлэх; хаагдсан хугацааны хэмжүүр шаардвал `completed_at`-д тулгуурлах. Бүх хугацааны KPI-г тусдаа гарчигтай бүлэг болгох. Код: `app/dashboard-panel.tsx`, `app/it-panel.tsx`, `app/marketing-panel.tsx`, харгалзах API report.

### 13. Өдөр тутмын ажлын өмнө хэт их давтагдсан мэдээлэл байна

Desktop sales дээр header, tabs, 4 KPI, notice, toolbar, filter-ийн дараа анхны мөр ойролцоогоор 720 px орчимд эхэлдэг. Mobile 844 px өндөрт хүсэлтийн анхны мөр хараахан хүрэхгүй. Админы dashboard-ийн “Батлах” ажлууд туршилтын зураглалд ~2883 px доор байрласан.

Санал: операторт compact work mode; KPI/зааврыг эвхэх; “Одоо хийх ажил”, “Батлах хүлээгдэж буй” жагсаалтыг дээр байрлуулах. Анхлан суралцагчийн зааврыг дахин нээх боломжтой тусламж руу шилжүүлэх.

### 14. Mobile хүснэгт өдөр тутмын үйлдэлд удаан

7 баганатай хүснэгтийн хариуцагч, дараагийн алхам, нээх үйлдэл нь өргөн дэлгэцэд ч урт Монгол тексттэй үед баруун талд гарна. Mobile дээр харилцагчийн мөр ба хэрэгтэй үйлдлийг холбож харах хэцүү. Horizontal table scroll өөрөө accessibility зөрчил гэсэн үг биш.

Санал: mobile lead card — нэр/утас, төлөв, тов, дараагийн үйлдэл, нээх товч. Desktop дээр баганын өргөн, wrap, sticky эхний багана/үйлдлийг хэрэгцээгээр шийдэх. Утасны дугаарт `tel:` болон copy үйлдэл санал болгох.

### 15. Маягтын алдаа, түгжигдсэн талбарын тайлбар дутуу

Хүсэлтийн submit алдаа голчлон toast-д гарна; field-level error mapping байхгүй. Засварын утас `readOnly` боловч UI нь editable талбартай ижил, учрыг нь тайлбарлаагүй. Дараагийн тов зэрэг нөхцөлт шаардлагууд бүх төлөвт адилхан харагдана.

Санал: буруу талбарын доор алдаа, `aria-invalid`, `aria-describedby`, эхний алдаа руу focus; утас түгжээний тайлбар; статусын дагуу товын шаардлагыг тодорхой харуулах. Алдааг текстээр тодорхойлох зарчим: [W3C Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html). Нотолгоо: [засварын form](04b-lead-edit.png), `app/crm.tsx`.

### 16. Зарим custom tab/control-ийн accessibility холбоос дутуу

Sheets source selector нь `role=tablist/tab` боловч өөрөө бүрэн keyboard navigation/tab-panel relationship хэрэгжүүлээгүй. Settings tab-уудын агуулгыг `TabsContent`-ийн оронд нөхцөлт section-оор харуулдаг. SMS RuleRow-ийн switch, textarea-д тусдаа accessible label холбоогүй.

Санал: нэг shared Tabs pattern ашиглах, panel ID/label-ийг холбох; switch/textarea бүрт тодорхой нэр өгөх. Keyboard Tab, Arrow, Home/End, Escape, focus restore-ийг гараар турших. Код: `app/sheets-panel.tsx`, `app/settings-panel.tsx`, `app/sms-rules-panel.tsx`.

### 17. Mobile чат дэлгэцийн зайг бүрэн ашиглахгүй

390 px дээр chat content ~373 px боловч conversation list **280 px** хэвээр, баруун талд хэрэггүй хоосон зайтай. Энэ нь mobile `.chat-list{width:100%}`-ийг дараах ерөнхий `width:280px` дарж байгаатай холбоотой. Зааварт “Зүүн талаас…” гэж бичсэн ч mobile дээр жагсаалт дээр байрлана. Draft `body` нь peer солиход цэвэрлэгдэхгүй/тусгаарлагдахгүй байгаа нь өөр хүнд зориулсан тексттэй шинэ чат нээх эрсдэлтэй; илгээлтийн алдаа гэж туршиж батлаагүй.

Санал: mobile дээр жагсаалт → харилцан яриа гэсэн хоёр дэлгэц, буцах товч; draft-ыг peer-ээр ялгах; гар нээгдэхэд composer харагдахыг бодит төхөөрөмжөөр шалгах. Нотолгоо: [mobile chat](10-chat-mobile.png), `app/chat-panel.tsx`, `app/globals.css`.

### 18. Google Sheets тохируулах эхний алхам доор дарагдсан

Холболтын ажиллагааны урт тайлбар, хоосон sync үзүүлэлтүүд, disabled товчнуудын дараа анхны credential тохиргоо орно. API scope, JSON, mapping зэрэг ойлголтыг нэг урт form-оор шаардаж байна. Техникийн админд боломжтой ч анхны тохиргооны дараалал сайн харагдахгүй.

Санал: “1. Эрх холбох → 2. Sheet сонгох → 3. Багана/ажилтан тулгах → 4. Турших → 5. Идэвхжүүлэх” урсгал. Advanced JSON mapping-ийг details хэсэгт байлгаж, sync-ийн хязгаарыг хэрэгтэй үед тайлбарлах. Нотолгоо: [Sheets дэлгэц](08b-sheets.png).

### 19. Экспортын хүрээ товчны нэрээс ойлгогдохгүй

“Экспорт” нь зөвхөн одоогийн `data.leads`, хамгийн ихдээ тухайн 50 мөрийн хуудсыг гаргана. Footer-т энэ тухай бичсэн нь сайн боловч хэрэглэгч товч дарах үед доорх тайлбарыг харахгүй байж болно. Импорт 100 мөрийн хязгаартай, preview эхний 5 мөрийг харуулдаг.

Санал: “Энэ хуудасны 50 хүсэлтийг экспортлох” гэж нэрлэх эсвэл “Энэ хуудас / Бүх шүүсэн үр дүн” сонголттой болгох. Импортод мөрийн дугаар, алдаа, нэмэх/алгасах тооны нэгдсэн урьдчилсан шалгалт харуулах. Код: `app/crm.tsx → download/ImportDialog`.

### 20. Устгалын хамгаалалт байгаа ч сэргээх зам байхгүй

Хүсэлтийн delete нь шалтгаан, баталгаажуулалттай; backend soft-delete хийдэг ч сэргээх интерфэйс байхгүй. Хэрэглэгчийн алдаатай устгалд админы гадуурх тусламж шаардлагатай. Бүх системд undo заавал хэрэгтэй гэсэн стандартын дүгнэлт биш; өгөгдөлд тулгуурласан CRM-ийн санал.

Санал: эрхтэй хэрэглэгчид зориулсан “Устгасан хүсэлт” хэсэг эсвэл хугацаатай undo. Хэрэв сэргээх бизнесийн бодлого байхгүй бол одоогийн буцаах боломжгүй тайлбарыг хадгалах. Код: `app/crm.tsx → DeleteLead`.

### 21. Жижиг typography ба icon target-уудыг нэг хэмжээсийн системд оруулах

Хүснэгтийн header 9 px, metadata/status/help-ийн олон хэсэг 10–11 px. Close/reaction зэрэг icon-only control-ийн target хэмжээг breakpoint, spacing-тэй нь нягтлах шаардлагатай. 9 px текстийг дангаар нь WCAG-ийн заавал зөрчил гэж тооцоогүй; contrast болон өдөр тутмын унших ачаалалтай хамт үнэлэв.

Санал: ажлын үндсэн текстийг 14–16 px, туслахыг 12–13 px орчимд хэрэглэгчээр турших; mobile гол үйлдлийг 44 px орчим болгох нь дизайны зорилт. WCAG 2.2 AA target-size нь 24×24 CSS px буюу заасан spacing/exception нөхцөлтэй; 44 px-ийг AA-ийн бүх control-д заавал босго гэж ойлгож болохгүй. [W3C Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### 22. Нэршил, огноо, зааврын хэл жигд биш

Browser дээр “September”, “AM”, `mm/dd/yyyy`, “Choose File” зэрэг English формат Монгол label-тай холилдсон. `Recycle`, “Дахин ажиллах”, “Дахин ажиллах бүлэг” гэсэн ойлголтууд шинэ ажилтанд ялгахад нэмэлт ачаалал үүсгэнэ. Team хуудсын “сайт хуваалцах эрх” тайлбар нь Google OAuth + идэвхтэй гишүүний урсгалтай нийцэж буй эсэхийг дахин шалгах хэрэгтэй.

Санал: date display-ийг тогтвортой `2026-09-18 09:30` эсвэл тодорхой Монгол форматтай болгох; native date/file control-ийн хэл browser-аас хамаардаг гэдгийг тооцож custom visible hint өгөх. Recycle-г нэг Монгол үндсэн нэртэй болгож, эхний хэрэглээнд товч тайлбарлах. Header-ийн “Хамгаалалттай орчин” зэрэг badge-ийг ажиллагааны бодит төлөвтэй андуурагдахгүй байлгах.

## Санал болгож буй мэдээллийн бүтэц

Одоогийн модулиудыг хадгалж дараах ажлын дарааллыг илүү тод болгоно:

| Хэрэглэгч | Нэвтэрсний дараах гол зорилго | Дэлгэцийн дээд хэсэг |
|---|---|---|
| Борлуулалтын ажилтан | Дараагийн харилцагчтай холбогдох | Хугацаа хэтэрсэн → одоо хийх → дараа хийх дараалал |
| Ахлах/удирдлага | Хуваарилах, саатал арилгах | Хуваарилагдаагүй, хугацаа хэтэрсэн, шийдвэр хүлээсэн |
| Админ/удирдлага | Батлах, системийн байдлыг харах | Батлах ажлууд, холбоосын алдаа, дараа нь тайлан |
| Маркетинг | Өөрийн ажил ба төсвийн шийдвэр | Идэвхтэй ажил, баталгаажилт, хугацаа |
| IT | Өөрийн ажлын дараалал | Хугацаа хэтэрсэн, идэвхтэй, шинээр ирсэн |

Desktop дээр одоогийн sidebar + workspace + detail sheet хэв маягийг хадгалж болно. Mobile дээр ажлын жагсаалт, өдрийн agenda, full-screen detail-ийг үндсэн болгох нь зохистой. Модуль доторх tab-уудыг хязгаарлагдсан scroll эсвэл сонгогчид багтаана.

## Засварын дараалал ба баталгаажуулалт

**Эхний ээлж — ажлыг тасалдуулж буй асуудал:** 01–06, 09–10. Overflow, KPI clipping, календарийн нээлт, contrast, алдааны state, filter semantics, hydration.

**Дараагийн ээлж — мэдээлэл хамгаалах:** 07–08, 11, 15, 20. Draft хамгаалалт, SMS-ийн explicit save, deep link, field error, сэргээх урсгал.

**Гурав дахь ээлж — өдөр тутмын хурд:** 12–14, 16–19, 21–22. Тайлангийн тайлбар, compact layout, mobile cards, a11y, чат, Sheets wizard, export, typography/нэршил.

Хугацааны амлалт өгөхийн өмнө responsive component засвар, draft persistence, URL routing-ийн ажлын хэмжээг тусад нь тооцно.

Засварын дараах зайлшгүй туршилт:

1. 320/360/390/768/1280/1440 px, урт нэр, их дүн, 0/1/50 мөр; page overflow ба тайрагдсан мэдээлэлгүй.
2. Бүх эрхээр sidebar, default page, module/tab, Back/Forward, refresh, lead deep link.
3. Form dirty → Escape/X/backdrop/navigation; хадгалах амжилт/алдаа; талбарын focus.
4. Календарийн +N, өдөр солих, сар солих, date filter, mobile agenda.
5. Offline/timeout/401/403/409/500 → үнэн зөв error, retry, session-expired message; хуучин мэдээлэл шинэ мэт харагдахгүй.
6. Keyboard-only, screen reader, focus order, dialog restore, accessible name, 200–400% zoom, contrast.
7. Бодит гар утасны keyboard, чат composer, file upload, date picker, notification permission.
8. CRM/IT/маркетинг/SMS/Sheets regression тестүүд болон production build. Lint/build амжилттай байх нь UX/UI алдааг дангаар илрүүлэхгүй.

## Хэрэглэгчээр баталгаажуулах санал

Борлуулалтын 3–5 ажилтан, нэг ахлах, нэг админд: шинэ хүсэлт бүртгэх, дуудлагын үр дүн хадгалах, 4+ ажилтай календарийн өдөр нээх, шүүлттэй экспорт хийх, төсөв батлах, SMS дүрэм засах даалгавар өгнө. Даалгаврын амжилт, хугацаа, буцах алхам, андуурсан үйлдлийг тэмдэглэж одоогийн ба засварын дараах хувилбарыг харьцуулна. Эдгээр хэмжилтийг энэ аудитад хийгээгүй; санал болгож буй дараагийн баталгаажуулалт юм.
